# Softmax V1：分块合并与 Spill 验证

## 算法

每行分成长度为 1,024 的块。每块计算两个 FP32 统计量：

```text
mₖ = max(xₖ)
lₖ = Σᵢ exp(xₖᵢ - mₖ)
```

一行所有块合并时：

```text
m = maxₖ(mₖ)
l = Σₖ lₖ × exp(mₖ - m)
```

最后再次读取输入，写出：

```text
yᵢ = exp(xᵢ - m) / l
```

必须把每块的 `lₖ` 乘以 `exp(mₖ-m)`，因为不同块的指数和使用了不同的基准最大值。
此合并公式与 Online Softmax 的归一化思想相关；当前实现使用并行的三阶段归约，
尚未采用单 Kernel 的在线扫描。

## 同一轮 Benchmark

| 形状 | PyTorch P50 | V0 P50 | V1 P50 | 本轮较快的 Triton 版本 |
|---:|---:|---:|---:|---|
| 4096×8192 | 338.43 μs | 331.26 μs | 510.43 μs | V0 |
| 2048×16384 | 406.56 μs | 333.82 μs | 510.98 μs | V0 |
| 1024×32768 | 631.81 μs | 1881.60 μs | 501.76 μs | V1 |
| 512×131072 | 1307.65 μs | 不支持 | 985.60 μs | V1 |

对 `1024×32768`，V1 相比 V0 快约 3.75 倍。短行使用三个 Kernel，额外启动与重复读取
的成本超过了分块带来的收益，因此不能用 V1 替代全部形状。当前测试把性能交叉区间
定位在行宽 16,384 到 32,768 之间；具体阈值仍依赖形状和 GPU。

完整数据保存在 `softmax_v0_v1_rtx3080ti_fp32.csv`。

## NCU：1024×32768，V1 三个阶段

每阶段独立采集，单位 MB 为 NCU 输出；三个阶段在不同 profiler 进程中运行，时间相加
仅用于解释主要成本，端到端延迟以 Benchmark 为准。

| 指标 | Stage 1 局部统计 | Stage 2 合并 | Stage 3 写出 |
|---|---:|---:|---:|
| Duration | 167.07 μs | 4.51 μs | 343.20 μs |
| DRAM Read | 135.62 MB | 265.60 KB | 137.51 MB |
| DRAM Write | 3.16 MB | 8.96 KB | 133.79 MB |
| Local Load | 0 B | 0 B | 0 B |
| Local Store | 0 B | 0 B | 0 B |

V1 合计实际 DRAM 读写约 410 MB，接近“读输入两遍、写输出一遍”的 402.65 MB 基线，
再加少量统计量及显存事务开销。同形状 V0 曾测得约 1,460 MB DRAM 流量，且 Local
Load/Store 约 1.21 GB。V1 消除了可观测的 Local Memory Spill。

Stage 3 最耗时，因为它再次读取整行、计算指数并写出概率。Stage 2 只处理每行 32 个
统计量，约 4.51 μs；目前无需优先优化它。

## 工程判断

- 中等行宽优先使用 V0；它只启动一次，读取输入一次。
- 超宽行使用 V1；分块工作集控制在 1,024 个元素，避免 V0 的 Spill。
- V1 的逻辑最低数据流量比 V0 高，因为它再次读取输入；但实际流量远低于发生 Spill
  的 V0。
- 此结果不能外推成固定的全平台切换阈值。需要对目标 GPU 和真实形状重新测量。
